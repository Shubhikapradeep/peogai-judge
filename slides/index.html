2. Problem Statement & Motivation
Automated Code Review Dilemma

The Context: LLM-as-a-Judge

  • Modern CI/CD pipelines need rapid, cost-effective automated code review to catch bugs before deployment.
  • LLM-as-a-Judge uses language models to grade candidate solutions, review PRs, and rank implementations.
  • Large commercial models (GPT-4) are expensive, high-latency, and leak proprietary code off-premise.

The Core Question & Risk

The Core Vulnerability: Can small, open-source models (≤ 7B) running locally on a laptop evaluate code reliably?

  • Does their judgment reflect actual code semantics or superficial cues?
  • If an evaluator suffers from position bias, flawed code gets merged simply because it was presented as "Answer A".

3. Literature Summary & Foundations
Related Work & Prior Benchmarks

MT-Bench & Chatbot Arena (Zheng et al., 2023)

  • First formalized LLM-as-a-judge for natural language dialogues.
  • Identified position bias, verbosity bias, and self-enhancement bias in GPT-4 and Claude.
  • Left code correctness evaluation largely unaddressed.

CodeJudgeBench (Chen et al., 2024)

  • Built an extensive benchmark of code generation and debugging pairs.
  • Ground-truth correctness established via automated hidden unit tests, not subjective human ratings.
  • Provides the baseline dataset for our study.
"Bias in the Loop" (Stureborg et al., 2024): Explored length and style biases in proprietary 70B+ LLMs. Edge-scale (≤ 7B) models remained unexplored in functional code auditing.

5. Research Questions (RQs)
Core Empirical Hypotheses
RQ1 (Pairwise & Pointwise Accuracy): How accurately can open-source 3B and 7B models determine code correctness under zero-shot prompt evaluation?
RQ2 (Position Bias): To what extent does the order of presentation sway the judge? How frequently do verdicts flip when the code order is reversed?
RQ3 (False Acceptance Rate): In single-code auditing (pointwise), what fraction of buggy solutions are erroneously approved (FAR)?
RQ4 (Mitigation Bounds): Can explicit prompt debiasing or majority voting ($N=3$) eliminate position bias, or is architectural order-averaging mandatory?

6. Scope: What We Did and Did Not Do
Clear Methodological Boundaries

What We Did

  • 150 balanced code pairs (300 programs): 50 Easy, 50 Medium, 50 Hard.
  • Full dual-order evaluation: Tested both Order 1 $(1,2)$ and Order 2 $(2,1)$ across all pairs.
  • 4 comprehensive experiments: Pairwise, Verbosity, Pointwise, and Fixes.
  • 2,400 total judge calls: Statistically evaluated with 95% Wilson CIs and McNemar paired tests.

What We Did Not Do (Why)

  • No proprietary closed APIs: Capped at 7B open weights to ensure local offline feasibility.
  • No self-enhancement test: Models did not judge their own self-generated code.
  • No subjective quality metrics: Excluded stylistic readability and security scores due to lack of objective test-suite ground truth.

9. Models & Experimental Setup
Reproducible Hardware & Inference Parameters

Evaluator Models

  • Qwen2.5-Coder-3B-Instruct: fp16 via vLLM on Colab T4; Q4_K_M GGUF on MacBook M3 Pro (Ollama).
  • Qwen2.5-Coder-7B-Instruct: 4-bit AWQ quantized via vLLM on Colab T4.
  • Same architecture family isolates scale as the single independent variable.

Decoding & Scale Parameters

  • Greedy decoding ($T=0$): Exp 1, 2, 3, and 4b; max 16 new tokens.
  • Sampling ($T=0.7$, $N=3$): Exp 4c majority voting.
  • Compute Cost: 2,400 total calls in 1.27 GPU-hours on single Tesla T4.
  • Parse robustness: 0.0% parse failures across all runs.

10. Experiments Overview
Four Targeted Experimental Regimes

Exp 1: Pairwise & Position Bias

Present candidates in both orders: $(1,2)$ and $(2,1)$. Measure accuracy gap, order consistency, and share of `A` verdicts.

Exp 2: Verbosity Perturbation

Pad incorrect code with docstrings/comments asserting correctness (AST-equivalent logic). Measure shift in win rate.

Exp 3: Pointwise Single-Code

Evaluate each of 300 answers individually (`correct` vs `incorrect`). Calculate False Acceptance Rate (FAR) & FRR.

Exp 4: Position Bias Mitigations

Compare baseline against 4a: Order-Averaging, 4b: Debias Prompt, and 4c: Vote@3 at $T=0.7$.

13. Key Findings & Limitations
Summary of Empirical Insights

Core Findings

  1. Extreme Position Bias: 3B picked position A in 96% of calls; 7B in 92%. In 92% of pairs, swapping candidate order flipped the decision!
  2. Severe Leniency in Pointwise Auditing: False Acceptance Rate reached 76%. Small LLMs rubber-stamp broken code.
  3. Order-Averaging is Mandatory: The only provable defense, boosting accuracy to 83.3% on agreed decisions.

Limitations & Constraints

  • Difficulty Label Noise: 82% of problems shared across generator splits had conflicting difficulty ratings in CodeJudgeBench.
  • Language & Scope: Evaluated on Python competitive programming; general enterprise codebases may have different token dynamics.
  • Model Scale Ceiling: Restricted to ≤ 7B parameters.
